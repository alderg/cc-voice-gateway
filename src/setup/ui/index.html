cc-voice-gateway setup

No HTTPS. This page and everything you type in it travel unencrypted. Use it only in your own network, or through an SSH tunnel: ssh -L 8790:localhost:8790 <server>, then open the link with localhost.

What the gateway needs. Red items marked "needed" must be fixed before the controller can run.

2. Gateway

The voice endpoint listens on 127.0.0.1 at this port; the tunnel or proxy forwards to it.

Every git repository directly in this folder gets a worker (on this computer, without Docker).

How many workers may run at once.

The rare approval the controller needs is read out in the car.

3. Models

The controller answers by voice, so speed counts: a smaller model or a lower effort answers sooner. Workers do the actual work in your repositories: a larger model and a higher effort pay off there. "Default" keeps Claude Code's own choice. Models and effort levels

Passed as --model and --effort by scripts/start-controller.sh.

Every worker run gets them, on this computer and in Docker.

4. Telegram optional

Results, questions and approvals reach your phone once voice mode has ended, and /stop locks the kill switch. Create a bot: in Telegram, write /newbot to @BotFather (how) and copy the token it gives you.

Then open your bot in Telegram, tap Start and send any message, for example "Hallo".

Unticked, a saved bot token and chat ID are deleted when you write the setup.

After this long without a voice call, voice mode counts as ended.

5. Workers in Docker optional

The workers run in a container that sees only one folder of clones, with the access the GitHub token gives them.

Its name, for example voice-workers.

Mounted as /repos. Not your own checkouts: git on this computer never runs in it.

Built from docker/ for your user id.

Claude Code's login in the container

On this computer run claude setup-token, sign in, and paste the long-lived token it prints (it starts with sk-ant-). About setup-token

GitHub token: it sets what workers may do

  • read-only, nothing leaves the container: no token for public repositories; for private ones a fine-grained token with only the chosen repositories and Contents: Read-only. Not a classic token: its repo scope can also write.
  • pr, draft pull requests: a fine-grained token with Contents and Pull requests: Read and write (Workflows only if workers should change workflow files), and the default branch protected by a ruleset that requires pull requests, with an empty bypass list. A classic token with repo works too, for all your repositories at once.
  • full, a direct push when you ask: the same token, and a default branch without such protection.

About personal access tokens. An organisation may have to approve a fine-grained token first.

Repositories in the container

They are cloned inside the container, over HTTPS. Already in the folder: none.

Forcing a lower level than the token allows is a rule for the workers, not a limit of the token.
